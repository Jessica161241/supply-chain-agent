### R1 · 跨节点信号能否传递？（2026-09-26 ~ 09-27 排查）

**风险等级**：🔴 高（方案最大技术风险点）

**风险描述**
`OrderingPolicy.compute_order(inventory_position, forecast_mean, forecast_std)`
的签名是**单节点局部决策接口**，没有跨节点参数钩子。如果框架完全不支持
跨节点信号传递，"聚合缺口信号上报 → 上级调整补货"这条核心创新就落不了地，
只能退而求其次手写仿真循环（`manual_stepper.py`）。

**排查方法**
1. 读源码：`deepbullwhip/chain/network_sim.py` 的 `simulate()` 主循环，
   重点看节点处理顺序与策略对象的生命周期；
2. 本地实测：搭一个 3 层拓扑（regional → city → store，T=40），
   各节点策略通过共享可变对象（`SignalBus`）互相读写信号，
   统计每期信号的读数是否非零。

**排查结论**：✅ **框架支持，不需要写 manual_stepper.py。**

**原理**
- 策略对象在 `NetworkSupplyChain.__init__` 里**一次性构造**，整个仿真期间常驻；
- `compute_order()` 每个时间步都会被调用一次；
- 因此只要在**构造策略时传入一个共享的可变对象**，各节点策略就能通过它
  互相读写，**完全不需要改框架**；
- 更关键的是**节点处理顺序天然正确**：`simulate()` 内部用反向拓扑序，
  即每个时间步内先处理 store → 再处理 city → 最后 regional，
  所以 store 在本步上报的信号，city 在同一步就能读到，
  **正是我们要的"自下而上"信息流方向**。

**实测证据**（3 层拓扑，T=40）
```
HOP 1  store -> city     : 非零读数 37 / 40 期
HOP 2  city  -> regional : 非零读数 37 / 40 期
```
（前 3 期读数为 0 是库存尚未消耗的启动瞬态，属正常。）

**对项目的影响**
`manual_stepper.py` 从"大概率要写的兜底方案"降级为"**低优先级备选**"。
B 同学的时间省下来做策略调优，而不是手写仿真循环。

**后续行动**
- 在 `src/coordination/signal_protocol.py` 定义 `SignalBus` 与信号数据结构；
- 在 `src/coordination/custom_policy.py` 实现协同策略；
- `manual_stepper.py` 保留为接口占位，不实现完整逻辑。

**遗留观察（重要）**
朴素的协同规则**不一定改善总成本**。POC 实测数据：
```
node                  BW基线   BW协同     成本基线   成本协同
store                   3.29     3.29          66         66
city_warehouse          6.61     5.14  ↓       69         78  ↑
regional_warehouse      1.80     1.30  ↓       69         61  ↓
TOTAL                                        203        206  ↑
```
两个上游节点的牛鞭系数都降了，但**总成本反而升了**（203 → 206）。
说明协同策略的收益完全取决于规则设计，B 同学需要做参数调优
（如 `alpha` 系数、信号定义），不能默认"加了协同就一定更好"。
这个对照实验也正好是路演里"我们做了 A/B 对比"的素材来源。

### R2 · 框架接口与需求文档不符（2026-09-24 ~ 09-25 构建拓扑时实测）

**风险等级**：🟡 中

**风险描述**
《方向二项目代码结构指南》里对框架接口的描述与 deepbullwhip 0.4.1 的
真实签名不一致，照抄会写错代码。构建 `src/network/topology.py` 时逐条撞上。

**排查方法**：用 `inspect.signature()` 打印真实签名 + 读源码。

**实测结论（与文档不符的 3 条）**

| # | 文档/初始写法 | 真实签名 |
|---|---|---|
| 1 | `EdgeConfig(source=..., target=...)` | ❌ 只有 `(lead_time, capacity, transport_cost)`，**不含连接关系** |
| 2 | `NetworkSupplyChain(echelons=[...], edges=[...], policy=...)` | ❌ 只接受 `graph`（一个 `SupplyChainGraph` 对象）+ `policies` 字典 |
| 3 | 边的连接关系由 `EdgeConfig` 定义 | ❌ 连接关系是 `SupplyChainGraph.edges` 字典的 **key** `(上游名, 下游名)` |

**正确用法**
```python
graph = SupplyChainGraph(
    nodes={名: EchelonConfig(...)},          # 节点表
    edges={(上游, 下游): EdgeConfig()},      # 边表，连接关系在 key 里
)
policies = {名: OrderUpToPolicy(lead_time=节点.lead_time) for 名 in nodes}
net = NetworkSupplyChain(graph=graph, policies=policies)
```

**连带发现**
- `OrderUpToPolicy.__init__(lead_time: int, service_level: float = 0.95)`
  —— `lead_time` 是**必需参数**，不能无参构造；
- `EdgeConfig.lead_time` 在仿真中**不生效**（对齐清单 §1.7），
  补货提前期必须配在节点的 `EchelonConfig.lead_time` 上。

**对项目的影响**
`src/network/topology.py` 已按真实接口重写，`03_topology_baseline.ipynb`
跑通验证（7 节点、6 条边、拓扑序正确）。

### R3 · 基线仿真暴露中间层缺货与牛鞭放大（2026-09-24 ~ 09-25 实测）

**风险等级**：🟢 低（是预期现象，反而是协同策略的动机）

**现象**
基线 `OrderUpTo` 策略在三层拓扑上跑完 365 天后：

| 层级 | 库存均值 | 牛鞭系数 |
|---|---|---|
| 区域仓 | -81.60（持续缺货） | 4.48 |
| 城市仓 1 | -21.88 | 4.66 |
| 城市仓 2 | -22.59 | 5.55 |
| 门店（4 个） | +5.91 ~ +6.37 | 1.37 ~ 1.64 |

总成本 22563.92，累计牛鞭 4.48。

**解读**
- 中间层持续负库存 = 整条链在"欠货"运行，上游补货跟不上下游订单；
- 门店牛鞭接近需求本身（1.4~1.6），但城市仓放大到 4.7~5.6，
  **上游看到的波动被逐级放大** —— 这正是牛鞭效应的典型表现。

**对项目的影响**
这是**协同策略的优化目标**：降低中间层牛鞭系数、减少缺货，
同时不显著增加总成本。也是路演里"为什么要做协同"的动机素材。

---

## 排查方法沉淀

1. **接口不明确时，先 `inspect.signature()` 打印真实签名**，不要猜参数名；
2. **读源码优先于读文档**——deepbullwhip 0.4.1 与任务书描述多处不符；
3. **每次实测结论都留档**（命令 + 输出），作为提交材料的证据；
4. **卡住超过半天必须同步团队**——R1 的排查就是 A 同学独立完成后同步给 B 的。
